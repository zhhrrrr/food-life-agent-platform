# 开发日志 042：秒杀已支付退款策略

## 本次目标

秒杀链路之前已经完成：

```text
秒杀活动查询
秒杀下单
Redis 库存预占
异步请求单
支付成功同步
未支付取消回滚
库存对账
链路聚合查询
```

但秒杀订单支付后的退款还没有单独扩展。之前退款接口虽然能把非拼团订单主表改成 `REFUNDED`，但不会同步 `seckill_order`，也不会恢复秒杀活动库存。

本次补齐秒杀已支付退款：

```text
dining_order.PAID -> REFUNDED
seckill_order.PAID -> REFUNDED
seckill_activity.stock + 1
```

## 业务流程

复用已有退款入口：

```http
POST /api/trade/orders/{orderId}/refund/mock
```

流程：

1. 退款责任链加载订单。
2. `UniqueRefundRuleFilter` 判断重复退款。
3. `RefundOrderRuleFilter` 校验订单必须是 `PAID`。
4. 按交易类型分流：

```text
NORMAL     普通购买退款
GROUP_BUY  拼团退款策略路由
SECKILL    秒杀退款策略路由
```

5. 秒杀退款策略执行仓储事务：

```text
dining_order.order_status = REFUNDED
seckill_order.order_status = REFUNDED
seckill_activity.stock = stock + 1
```

6. 返回退款结果，响应里带 `activityId`，方便前端或后续工具侧追踪秒杀来源。

## 为什么用策略

这次没有把秒杀退款塞进普通退款逻辑里继续堆 `if`。

当前退款主流程已经是：

```text
责任链做公共校验
不同业务类型用策略处理自己的逆向规则
```

所以秒杀也补一个策略入口：

```text
SeckillRefundStrategyRouter
ISeckillRefundStrategy
AbstractSeckillRefundStrategy
PaidSeckillRefundStrategy
```

虽然现在秒杀只有一个“已支付退款”策略，但它和拼团退款保持同一种组织方式。后续如果要加“秒杀已核销不可退”“秒杀支付超时退款”“部分退”等场景，可以继续往策略里扩。


## 数据一致性

秒杀退款必须同时改主订单和秒杀订单关系表，不能只改 `dining_order`：

```text
dining_order 是交易主单
seckill_order 是秒杀业务单
```

如果只改主单，查询秒杀链路时会出现：

```text
主订单 REFUNDED
秒杀单 PAID
库存没有恢复
```

所以本次把三件事放到同一个本地事务：

```text
改主订单
改秒杀订单
恢复 MySQL 秒杀库存
```

Redis 秒杀库存由既有库存对账能力兜底刷新：

```http
POST /api/trade/seckill/activities/{activityId}/stock/reconcile
```

## 当前边界

当前仍然是模拟退款，没有真实支付渠道退款单。

已完成：

```text
秒杀已支付退款策略
主订单和秒杀订单事务同步
秒杀活动库存回补
重复退款沿用退款责任链
退款响应返回 activityId
```

暂未做：

```text
真实支付渠道退款
退款单表
退款状态机
退款失败重试
退款通知 MQ
秒杀已核销售后规则
```

这些放到真实支付/售后骨架阶段统一处理。
