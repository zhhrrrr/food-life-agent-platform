# 开发日志-035：支付单与回调骨架

## 一、开发目标

本次继续只做非 Agent 业务。

之前支付接口是：

```http
POST /api/trade/orders/{orderId}/pay/mock
```

它直接把“支付成功结果”送进订单结算链，适合早期验证订单状态流转，但不够像生产环境。

本次新增支付单骨架：

```text
发起支付 -> 生成 payment_order
渠道支付成功 -> 回调 trade-service
trade-service 幂等更新支付单
支付单成功后调用已有订单支付结算链
重复回调直接返回 repeat
```

真实微信/支付宝后续只需要替换渠道适配器和验签逻辑，订单结算链不用推倒。

## 三、新增接口

### 1. 发起支付单

```http
POST /api/trade/pay/orders/{orderId}/prepare
```

请求：

```json
{
  "source": "FOOD_LIFE",
  "channel": "MOCK_PAY"
}
```

业务规则：

```text
必须登录
只能为自己的订单发起支付
订单必须是 WAIT_PAY
同一用户同一订单重复发起支付，返回已有支付单
```

### 2. 模拟支付成功回调

```http
POST /api/trade/pay/callback/mock
```

请求：

```json
{
  "payOrderNo": "PAY178662547779622409cbd",
  "outTradeNo": "OUT-PAY-46-001",
  "payAmount": 16800
}
```

业务规则：

```text
回调入口不要求登录
支付金额必须和 payment_order.pay_amount 一致
payment_order 通过 PREPARED -> SUCCESS 做 CAS 幂等
第一次成功回调触发订单支付结算链
重复回调返回 callbackBehavior = repeat，不重复结算订单
```

### 3. 查询支付单

```http
GET /api/trade/pay/orders/{payOrderNo}
```

## 六、当前结论

支付部分仍然是模拟渠道，但已经不是简单直接改订单状态。

现在具备生产化支付骨架：

```text
支付单可落库
支付单可查询
支付回调可幂等
回调入口和用户登录解耦
订单结算链继续复用已有责任链
普通购买支付成功后继续确认销量
```
