# 开发日志 006：套餐交易快照接口

## 一、本次开发目标

本次在 `feature/business-trade-snapshot` 分支开发 business 服务的套餐交易快照接口。

目标是为后续 `food-trade-service` 下单提供可信业务数据。

交易服务下单时不能相信前端传入的：

```text
店铺名称
套餐名称
套餐价格
库存
使用规则
```

这些数据必须从 `food-business-service` 查询。

## 二、本次新增接口

接口：

```http
GET /api/package/trade-snapshot/{packageId}
```

示例：

```http
GET http://localhost:8201/api/package/trade-snapshot/1
```

成功返回：

```json
{
  "code": "0000",
  "message": "success",
  "data": {
    "shopId": 1,
    "shopName": "Chengdu Spicy Hot Pot",
    "packageId": 1,
    "packageName": "Two-person Hot Pot Set",
    "packageDescription": "Beef, vegetables, snacks and drinks for two.",
    "coverImage": "",
    "price": 16800,
    "originalPrice": 23800,
    "stock": 100,
    "packageStatus": 1,
    "useRule": "Valid for dine-in only. Not available on public holidays."
  }
}
```

失败返回：

```json
{
  "code": "404",
  "message": "package not found",
  "data": null
}
```

## 九、为什么这个接口重要

后续 `food-trade-service` 创建订单时，需要保存订单快照。

订单快照应该来自 business 服务，而不是前端。

后续订单明细可以保存：

```text
shop_id
shop_name_snapshot
package_id
package_name_snapshot
package_price_snapshot
cover_image_snapshot
use_rule_snapshot
```

这样即使后面商家修改套餐名、价格、图片，也不会影响历史订单。

## 十、下一步建议

下一步可以开始开发：

```text
food-trade-service
```

第一版只做普通购买订单。

建议链路：

```text
1. 用户携带 Token 请求 trade-service
2. trade-service 从 UserHolder 获取 userId
3. trade-service 调用 business-service 的 trade-snapshot 接口
4. trade-service 创建 dining_order 和 dining_order_item
5. 返回订单号
```
