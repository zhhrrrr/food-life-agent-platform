# 开发日志-076-用户端交易闭环补齐

## 本次目标

在不涉及 Agent 能力的前提下，补齐用户端前端对真实后端交易链路的调用，让订单不再停留在“只能创建、只能查看”的阶段，而是可以从页面上完成支付、取消、退款、核销这些核心状态流转。

## 为什么先做这一步

当前后端的普通购买、拼团、秒杀、支付单、退款、核销、库存补偿、RabbitMQ 事件都已经有业务实现；但前端订单页只调用了订单列表接口，没有把这些能力暴露给用户。

这会导致一个问题：后端链路虽然能通过接口或脚本验证，但产品侧不是一个完整可用的 C 端应用。补齐订单操作后，前端可以真实触发 Gateway、认证、trade-service、business-service、RabbitMQ、本地消息表、库存幂等记录这些微服务链路。

## 本次新增和调整

### 1. 交易 API 补齐

文件：`food-life-agent-web/src/api/trade.ts`

新增接口：

- `preparePayment(orderId)`：调用 `POST /trade-api/pay/orders/{orderId}/prepare`
- `mockPaymentCallback(data)`：调用 `POST /trade-api/pay/callback/mock`
- `cancelOrder(orderId)`：调用 `POST /trade-api/orders/{orderId}/cancel`
- `confirmRefund(orderId)`：调用 `POST /trade-api/orders/{orderId}/refund/confirm`
- `useOrder(orderId)`：调用 `POST /trade-api/orders/{orderId}/use/mock`

说明：

- 前端仍然通过 Vite 代理访问 Gateway：
  - `/trade-api/**` -> `http://localhost:8080/api/trade/**`
- Axios 请求拦截器会自动带上 `authorization` token。
- Gateway 会做用户请求鉴权、traceId、日志、路由转发、限流等横切逻辑。

### 2. 订单类型补齐

文件：`food-life-agent-web/src/types/order.ts`

新增 TypeScript 类型：

- `PaymentPrepareRequest`
- `PaymentOrderResponse`
- `PaymentCallbackRequest`
- `PaymentCallbackResponse`
- `PaySettlementResponse`
- `CancelOrderResponse`
- `RefundOrderResponse`
- `UseOrderResponse`

说明：

- 类型字段与后端 DTO 对齐。
- 前端调用支付、退款、核销时不再使用 `any`，避免后续联调时字段写错。

### 3. 订单卡片增加业务动作

文件：`food-life-agent-web/src/components/OrderCard.vue`

新增状态动作：

- `WAIT_PAY`：
  - `立即支付`
  - `取消订单`
- `PAID`：
  - `到店核销`
  - `申请退款`
- `USED / CANCELED / REFUNDED`：
  - 只展示结果态，不提供继续操作

说明：

- 订单卡片只负责展示和抛出事件，不直接写业务调用。
- 页面组件负责业务编排，这样组件职责更干净。

### 4. 我的订单页接入真实业务编排

文件：`food-life-agent-web/src/views/OrdersView.vue`

新增方法：

- `handlePay(order)`
  - 准备支付单
  - 构造本地 mock 第三方交易号
  - 调支付回调
  - 刷新订单列表
- `handleCancel(order)`
  - 二次确认
  - 取消订单
  - 释放库存/补偿由后端领域服务处理
- `handleRefund(order)`
  - 二次确认
  - 退款确认
  - 回退支付状态、订单状态、库存、拼团/秒杀相关状态由后端处理
- `handleUse(order)`
  - 二次确认
  - 到店核销
  - 后端写核销记录并变更订单状态

说明：

- 每个订单操作会设置 `busyOrderId`，防止重复点击。
- 操作完成后重新加载订单列表，保证页面展示与后端状态一致。

### 5. 样式补充

文件：`food-life-agent-web/src/styles/main.css`

新增：

- `.order-card__actions`

说明：

## 完整请求链路示例

以“用户点击立即支付”为例：

1. 用户在前端订单页点击 `立即支付`
2. `OrderCard.vue` 抛出 `pay` 事件
3. `OrdersView.vue` 执行 `handlePay`
4. `trade.ts` 调用 `preparePayment(orderId)`
5. 请求进入 Gateway
6. Gateway 执行：
   - CORS
   - 白名单/黑名单判断
   - authorization token 校验
   - traceId 生成
   - 请求日志
   - Sentinel Gateway 限流
   - Token 透传
7. Gateway 路由到 `food-trade-service`
8. `PaymentController.preparePayment`
9. `PaymentOrderService.preparePayment`
10. 创建或复用支付单
11. 发布 `payment.created` 事件
12. 前端拿到 `payOrderNo`
13. 前端调用 `mockPaymentCallback`
14. Gateway 再次转发到 `food-trade-service`
15. `PaymentController.mockPaySuccessCallback`
16. Sentinel 对支付回调接口限流
17. `PaymentOrderService.handlePaySuccessCallback`
18. 支付单状态更新为成功
19. 调用 `OrderPaySettlementService`
20. 订单支付结算责任链执行
21. 普通订单变更为 `PAID`
22. business-service 套餐库存确认售出
23. 本地消息表记录库存确认消息
24. RabbitMQ 发布支付成功和订单已支付事件
25. 前端刷新订单列表，页面显示 `已付款`

## 当前边界

这一步仍然保留本地 mock 支付通道：

- 支付准备是真实业务接口
- 支付回调是真实后端回调处理逻辑
- 第三方支付渠道暂时是 `LOCAL_MOCK_PAY`

后续接真实支付时，只需要替换支付渠道适配层和回调验签，不需要推翻订单、库存、消息、状态流转主链路。
