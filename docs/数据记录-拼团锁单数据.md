# 数据记录 - 拼团锁单数据

## 数据库

- 服务：`food-trade-service`
- 数据库：`food_trade_db`
- 本次新增表：`group_buy_activity`、`group_buy_order`、`group_buy_order_list`
- 订单主表仍使用：`dining_order`
- 订单明细表仍使用：`dining_order_item`

## 表职责

| 表 | 职责 |
| --- | --- |
| `group_buy_activity` | 记录某个美食套餐是否参加拼团、成团人数、用户参与限制、拼团价、活动库存和有效期 |
| `group_buy_order` | 记录一支拼团队伍，包含 `team_id`、目标人数、锁定人数、支付完成人数、队伍状态 |
| `group_buy_order_list` | 记录用户参与拼团的明细，关联用户、队伍、交易订单、活动、套餐和支付成功时间 |
| `dining_order` | 统一交易订单主表，本次拼团订单的 `trade_type = GROUP_BUY` |
| `dining_order_item` | 统一交易订单明细，保存套餐交易快照 |

## 初始化数据

`group_buy_activity` 初始化一条本地拼团活动：

| 字段 | 值 |
| --- | --- |
| `package_id` | `1` |
| `activity_name` | `双人火锅套餐拼团` |
| `target_count` | `2` |
| `user_take_limit` | `1` |
| `group_price` | `12800` |
| `activity_status` | `1` |
| `valid_start_time` | `2026-01-01 00:00:00` |
| `valid_end_time` | `2026-12-31 23:59:59` |
| `stock` | `100` |

## 拼团锁单写入关系

1. 首次开团：创建 `group_buy_order`，生成新的 `team_id`，`lock_count = 1`。
2. 参与已有团：更新已有 `group_buy_order.lock_count = lock_count + 1`。
3. 创建交易订单：写入 `dining_order`，`trade_type = GROUP_BUY`，`order_status = WAIT_PAY`。
4. 创建订单明细：写入 `dining_order_item`，保存套餐名称、门店、封面、价格、使用规则快照。
5. 创建拼团明细：写入 `group_buy_order_list`，记录用户和队伍的锁单关系，`order_status = LOCKED`，`out_trade_time = NULL`。

## 拼团支付写入关系

1. 支付成功：`dining_order.order_status` 从 `WAIT_PAY` 更新为 `PAID`。
2. 参团明细：`group_buy_order_list.order_status` 从 `LOCKED` 更新为 `PAID`，并写入 `out_trade_time`。
3. 队伍进度：`group_buy_order.complete_count = complete_count + 1`。
4. 成团判断：当 `complete_count >= target_count`，`group_buy_order.team_status` 更新为 `SUCCESS`。
5. 支付结算会校验队伍仍在有效期内：`group_buy_order.valid_end_time > out_trade_time`。

## 拼团未支付取消写入关系

1. 取消主订单：`dining_order.order_status` 从 `WAIT_PAY` 更新为 `CANCELED`。
2. 取消参团明细：`group_buy_order_list.order_status` 从 `LOCKED` 更新为 `CANCELED`。
3. 回退队伍锁单人数：`group_buy_order.lock_count = lock_count - 1`。
4. 恢复活动库存：`group_buy_activity.stock = stock + 1`。
5. 用户参与次数统计只统计 `LOCKED`、`PAID`，已取消记录不再占用 `user_take_limit`。

## 拼团已支付退款写入关系

### 已支付未成团退款

对应 xfg 拼团 `Paid2RefundStrategy`。

1. 退款主订单：`dining_order.order_status` 从 `PAID` 更新为 `REFUNDED`。
2. 退款参团明细：`group_buy_order_list.order_status` 从 `PAID` 更新为 `REFUNDED`。
3. 回退队伍进度：`group_buy_order.lock_count = lock_count - 1`，`complete_count = complete_count - 1`。
4. 恢复活动库存：`group_buy_activity.stock = stock + 1`。
5. 队伍状态保持 `IN_PROGRESS`。

### 已支付已成团退款

对应 xfg 拼团 `PaidTeam2RefundStrategy`。

1. 退款主订单：`dining_order.order_status` 从 `PAID` 更新为 `REFUNDED`。
2. 退款参团明细：`group_buy_order_list.order_status` 从 `PAID` 更新为 `REFUNDED`。
3. 回退队伍进度：`group_buy_order.lock_count = lock_count - 1`，`complete_count = complete_count - 1`。
4. 如果退款前 `complete_count > 1`，队伍状态更新为 `COMPLETE_FAIL`。
5. 如果退款前 `complete_count = 1`，队伍状态更新为 `FAILED`。
6. 按 xfg 已成团退款逻辑，当前不恢复活动库存。

## 拼团超时补偿写入关系

触发入口：

```http
POST /api/trade/group-buy/timeout/compensate
```

定时任务默认每 60 秒扫描一次：

```yaml
food.trade.group-buy.timeout-compensation.enabled: true
food.trade.group-buy.timeout-compensation.fixed-delay-ms: 60000
```

补偿扫描条件：

1. `group_buy_order.team_status = IN_PROGRESS`。
2. `group_buy_order.valid_end_time <= 当前时间`。

单队伍补偿事务：

1. 队伍状态：`group_buy_order.team_status` 从 `IN_PROGRESS` 更新为 `FAILED`。
2. 队伍计数：`group_buy_order.lock_count = 0`，`complete_count = 0`。
3. 未支付锁单：`group_buy_order_list.order_status` 从 `LOCKED` 更新为 `CANCELED`。
4. 未支付主订单：`dining_order.order_status` 从 `WAIT_PAY` 更新为 `CANCELED`。
5. 已支付未成团：`group_buy_order_list.order_status` 从 `PAID` 更新为 `REFUNDED`。
6. 已支付主订单：`dining_order.order_status` 从 `PAID` 更新为 `REFUNDED`。
7. 活动库存：对本队伍中所有仍处于 `LOCKED` 或 `PAID` 的明细统一恢复库存，`group_buy_activity.stock = stock + 补偿明细数`。

说明：

- 超时补偿只处理未成团队伍，不处理 `SUCCESS` 已成团队伍。
- 已成团后的售后退款仍走拼团退款策略，不走超时补偿。
- 当前是 Java 侧本地定时任务，后续可以替换为 XXL-JOB、MQ 延迟消息或 Agent 调度工具。
