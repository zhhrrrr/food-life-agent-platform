# 开发日志-077-统一错误码与异常治理

## 本次目标

补齐非 Agent 阶段里非常关键的一块工程治理：统一错误码、统一异常兜底、Gateway 错误响应格式收敛。

这一步的核心不是新增业务，而是让前端、服务间调用、后续 Agent 工具调用都能获得稳定、可判断的错误语义。

## 背景问题

之前项目里存在三类问题：

1. `Response.success` 里直接写死 `"0000"` 和 `"success"`。
2. Controller 里散落很多 `Response.fail("400", e.getMessage())`。
3. Gateway 鉴权失败、黑名单拦截、Sentinel 限流各自手写 JSON 字符串。

这些代码能跑，但越往公司级项目演进，问题越明显：

- 前端只能靠字符串判断错误。
- Feign fallback 和 Agent 工具调用很难区分参数错误、资源不存在、未登录、限流、服务繁忙。
- Gateway 和业务服务可能返回不同格式。
- 新接口容易继续复制旧写法。

## 异常归类规则

当前领域层大量使用 `IllegalArgumentException` 表达业务拒绝，所以全局处理器做了轻量归类：

- message 包含 `not login` 或 `not logged in` -> `401`
- message 包含 `not found` -> `404`
- 其他参数或业务校验失败 -> `400`

这不是最终最完美的方式，但适合当前项目平滑演进。后续可以继续把核心领域异常升级成明确的业务异常类型，例如：

- `BusinessException`
- `NotFoundException`
- `ForbiddenException`
- `ServiceBusyException`

## 对后续 Agent 的价值

Agent 后续调用业务接口时，最怕返回语义不稳定。

现在至少可以稳定区分：

- `400`：参数错误或业务规则不满足
- `401`：用户未登录
- `403`：越权或内部接口保护
- `404`：业务资源不存在
- `429`：限流，需要稍后重试
- `503`：服务繁忙、熔断或下游不可用
- `500`：系统未知异常，需要人工排查

这样 Agent 工具层可以做不同策略：

- 400/404：提示用户修正输入
- 401：要求用户重新登录
- 403：禁止继续调用
- 429/503：可以有限重试或降级回答
- 500：记录任务失败并提示系统异常

## 当前边界

这一步没有一次性清理所有 Controller 的 `try/catch`，原因是当前业务 Controller 很多，直接大面积替换会带来不必要风险。

当前采取的公司里更常见的渐进方式：

1. 先提供统一错误码。
2. 先提供全局异常兜底。
3. 新代码优先走统一异常。
4. 高频链路先迁移，低频链路逐步迁移。
