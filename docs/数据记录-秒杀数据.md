# 数据记录 - 秒杀数据

## 数据库

- 服务：`food-trade-service`
- 数据库：`food_trade_db`
- 新增表：`seckill_activity`、`seckill_order`
- 主订单仍使用：`dining_order`
- 订单明细仍使用：`dining_order_item`

## 表职责

| 表 | 职责 |
| --- | --- |
| `seckill_activity` | 记录套餐秒杀活动、秒杀价、活动时间窗、库存、用户限购 |
| `seckill_order` | 记录用户抢购成功后和交易订单的关系 |
| `dining_order` | 统一交易订单主表，秒杀订单 `trade_type = SECKILL` |
| `dining_order_item` | 统一交易订单明细，保存套餐交易快照 |

## 初始化数据

`seckill_activity` 本地初始化一条活动：

| 字段 | 值 |
| --- | --- |
| `package_id` | `1` |
| `activity_name` | `local seckill meal package` |
| `seckill_price` | `9800` |
| `activity_status` | `1` |
| `valid_start_time` | `2026-01-01 00:00:00` |
| `valid_end_time` | `2026-12-31 23:59:59` |
| `stock` | `20` |
| `user_take_limit` | `1` |

## 秒杀下单写入关系

接口：

```http
POST /api/trade/orders/seckill
```

请求：

```json
{
  "activityId": 1,
  "quantity": 1
}
```

写入流程：

1. 校验用户登录。
2. 校验 `activityId` 存在。
3. 校验 `quantity = 1`。
4. 校验活动启用、活动已开始、活动未结束、库存大于 0。
5. 校验当前用户在该活动下未超过 `user_take_limit`。
6. 远程查询套餐交易快照。
7. 按套餐原价计算 `total_amount`，按秒杀价计算 `pay_amount`。
8. 原子扣减秒杀活动库存：`seckill_activity.stock = stock - 1`。
9. 写入 `dining_order`，`trade_type = SECKILL`，`order_status = WAIT_PAY`。
10. 写入 `dining_order_item`。
11. 写入 `seckill_order`，`order_status = WAIT_PAY`。

## 秒杀支付写入关系

秒杀支付复用：

```http
POST /api/trade/orders/{orderId}/pay/mock
```

写入流程：

1. `dining_order.order_status` 从 `WAIT_PAY` 更新为 `PAID`。
2. `seckill_order.order_status` 从 `WAIT_PAY` 更新为 `PAID`。
3. 支付响应返回 `activityId`，便于 Agent 追踪业务来源。

## 秒杀未支付取消写入关系

秒杀取消复用：

```http
POST /api/trade/orders/{orderId}/cancel
```

写入流程：

1. `dining_order.order_status` 从 `WAIT_PAY` 更新为 `CANCELED`。
2. `seckill_order.order_status` 从 `WAIT_PAY` 更新为 `CANCELED`。
3. 恢复秒杀库存：`seckill_activity.stock = stock + 1`。

## 当前边界

- 当前是 MySQL 原子扣库存版本，没有引入 Redis 预热、Lua 扣减、MQ 异步下单。
- 当前只允许 `quantity = 1`。
- 当前用户限购以 `seckill_order` 的 `WAIT_PAY / PAID` 记录统计。
- 当前秒杀退款仍未单独扩展，后续可以按拼团退款策略继续补。
