# 缓存治理与压测方案

## 缓存治理

当前已落地到 `food-business-service`：

| 缓存对象 | Key | TTL | 策略 | 失效时机 |
| --- | --- | --- | --- | --- |
| 店铺详情 | `food:cache:shop:{shopId}` | 10 分钟 | 旁路缓存 | 评价摘要变化、店铺销量变化 |
| 套餐详情 | `food:cache:package:{packageId}` | 5 分钟 | 旁路缓存 | 库存预占/释放、销量确认/回滚、运营调库存 |
| 店铺套餐列表 | `food:cache:shop:{shopId}:packages` | 3 分钟 | 旁路缓存 | 套餐库存/销量变化 |
| 套餐交易快照 | `food:cache:package:{packageId}:trade-snapshot` | 2 分钟 | 旁路缓存 | 套餐库存/销量变化 |

更新策略：

1. 读请求先查 Redis，未命中再查 MySQL 并回写缓存。
2. 库存、销量、评价摘要更新后先删除缓存。
3. 1 秒后再删除一次，降低并发读写导致旧数据回填的概率。
4. 运营接口可调用 `/api/business/operations/cache/preheat` 预热指定店铺或套餐。

后续可继续增强：

- 热点 Key 使用本地缓存或 Redis 多副本读。
- 空值缓存防穿透。
- 商品大促前按活动维度批量预热。
- 缓存变更事件通过 RabbitMQ 广播给其它节点做失效。

## 压测验证

脚本位置：

| 脚本 | 链路 | 重点观察 |
| --- | --- | --- |
| `scripts/k6/normal-order.js` | 普通下单 | 下单 QPS、库存远程调用、Sentinel 用户限流 |
| `scripts/k6/group-buy-order.js` | 拼团锁单 | 锁单吞吐、成团竞争、超时补偿 |
| `scripts/k6/seckill-order.js` | 秒杀异步请求单 | Redis 预扣、热点参数限流、请求单积压 |

运行示例：

```powershell
.\scripts\run-k6-food-flows.ps1 -AuthToken "<登录后的 token>" -PackageId 1 -ActivityId 1
```

压测前建议记录：

1. Gateway Sentinel 是否限流。
2. trade-service Sentinel 是否限流。
3. Redis 秒杀库存是否先于数据库承压。
4. RabbitMQ 队列是否出现积压。
5. Grafana 中 `http.server.requests`、`food_mq_consume_duration`、Feign 耗时是否异常。

RabbitMQ DLQ 改造后，如果本地已经存在旧队列，需要先重建项目队列拓扑：

```powershell
.\scripts\reset-rabbitmq-food-topology.ps1
```

执行后重启 business-service 和 trade-service，服务启动时会重新声明带 DLQ 参数的新队列。

面试讲法：

- 没有限流时，请求会直接进入数据库和远程库存链路。
- 加 Gateway 限流后，流量先在入口被削峰。
- 加接口级和用户级限流后，单用户刷单不会拖垮整体服务。
- 秒杀异步化后，用户请求只创建请求单并预扣 Redis，真正创建订单由后台消费/扫描完成。
