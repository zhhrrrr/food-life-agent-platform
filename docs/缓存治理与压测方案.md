# 缓存治理与压测方案

## 一、缓存治理

当前缓存治理落在 `food-business-service`，优先覆盖用户高频读链路和下单前的套餐快照链路。

| 缓存对象 | Redis Key | TTL | 策略 | 失效时机 |
| --- | --- | --- | --- | --- |
| 店铺详情 | `food:cache:shop:{shopId}` | 10 分钟 | 旁路缓存 | 店铺销量、评价摘要变化 |
| 套餐详情 | `food:cache:package:{packageId}` | 5 分钟 | 旁路缓存 | 库存预占、释放、销量确认、销量回滚、运营调库存 |
| 店铺套餐列表 | `food:cache:shop:{shopId}:packages` | 3 分钟 | 旁路缓存 | 套餐库存或销量变化 |
| 套餐交易快照 | `food:cache:package:{packageId}:trade-snapshot` | 2 分钟 | 旁路缓存 | 套餐库存或销量变化 |

## 二、缓存读写流程

1. 查询店铺、套餐、交易快照时先查 Redis。
2. Redis 未命中时查询 MySQL。
3. MySQL 查询成功后回写 Redis，并设置较短 TTL。
4. 库存、销量、评价摘要发生变更时，先删除相关缓存。
5. 变更完成 1 秒后再次删除，降低并发读写导致旧值回填的概率。
6. 运营端可以调用 `/api/business/operations/cache/preheat` 对指定店铺或套餐做预热。

## 三、后续可继续增强

- 热点 Key 使用本地缓存加 Redis 多级缓存。
- 空值缓存防止缓存穿透。
- 大促前按活动维度批量预热。
- 缓存变更事件通过 RabbitMQ 广播，让多实例节点统一失效。
- 对超热点套餐增加互斥锁或逻辑过期，降低缓存击穿风险。

## 四、k6 安装与运行

k6 使用项目本地安装方式，二进制放在 `tools/k6/k6.exe`。`tools/` 已被 `.gitignore` 忽略，不会提交到 Git。

安装脚本：

```powershell
.\scripts\install-k6-local.ps1
```

运行三条业务压测链路：

```powershell
.\scripts\run-k6-food-flows.ps1 -Profile smoke -PackageId 1 -ActivityId 1
```

`smoke` 用于本地低强度验证，`load` 用于正式压测：

```powershell
.\scripts\run-k6-food-flows.ps1 -Profile load -PackageId 1 -ActivityId 1
```

如果不传 `-AuthToken`，脚本会自动调用黑马点评式登录接口，读取 Redis 验证码，再拿到 token 后执行压测。

## 五、压测脚本

| 脚本 | 链路 | 重点观察 |
| --- | --- | --- |
| `scripts/k6/normal-order.js` | 普通下单 | 下单 QPS、库存远程调用、Sentinel 用户限流 |
| `scripts/k6/group-buy-order.js` | 拼团锁单 | 锁单吞吐、成团竞争、超时补偿 |
| `scripts/k6/seckill-order.js` | 秒杀异步请求单 | Redis 预扣、热点参数限流、请求单积压 |

## 六、观测指标

压测时重点看：

1. Gateway Sentinel 是否先拦截入口流量。
2. trade-service Sentinel 是否限制下单热点。
3. Redis 秒杀库存是否先于数据库承压。
4. RabbitMQ 队列是否出现积压。
5. Grafana 中 `http.server.requests`、`food_mq_consume_duration`、Feign 调用耗时是否异常。

## 七、RabbitMQ 队列重建

如果本地已经存在旧队列，而代码新增了 DLX/DLQ 参数，需要先重建项目相关队列：

```powershell
.\scripts\reset-rabbitmq-food-topology.ps1
```

执行后重启 `business-service` 和 `trade-service`，服务启动时会重新声明带 DLQ 参数的新队列。
