## 1. 两个退款不足与修复结果

| 原来的不足 | 实际后果 | 修复机制与核心文件 |
|---|---|---|
| 退款失败状态和失败原因写在业务事务内，抛异常后一起回滚；调用直接抛异常时甚至没有记录结果 | 无法可靠看到失败，也缺少自动补偿入口 | [RefundJournalService](../food-trade-service/food-trade-domain/src/main/java/com/foodlife/trade/domain/order/payment/service/RefundJournalService.java) 通过独立 `REQUIRES_NEW` 事务保存请求、处理中状态、成功或失败结果；[PaymentRefundService](../food-trade-service/food-trade-domain/src/main/java/com/foodlife/trade/domain/order/payment/service/PaymentRefundService.java) 捕获异常并单独落库 |
| 支付宝已退款，本地事务却失败；只有稳定退款号，没有主动修复链路 | 钱已退，支付单、业务单或库存仍未完成退款 | 先提交退款请求，支付宝调用在 `NOT_SUPPORTED` 阶段执行；[RefundRecoveryService](../food-trade-service/food-trade-domain/src/main/java/com/foodlife/trade/domain/order/payment/service/RefundRecoveryService.java) 扫描未完成记录，使用同一个退款号查单，继续完成本地支付和业务补偿 |

成功确认包含退款请求号、商户交易号、支付宝交易号和退款金额校验。查询接口的 `10000` 仅代表查询操作成功，只有 `REFUND_SUCCESS` 才确认退款成功。真实沙箱对于不存在的退款请求可返回 `10000` 和空退款字段，代码已处理这一情况，避免阻塞首次退款。[支付宝退款查询说明](https://aipay.alipay.com/docs/vibe-pay/ai-web-app-payment-qianyi/api-list/alipay-trade-fastpay-refund-query.html)

稳定退款号为 `RF + pay_order_no`；同一支付单只支持一笔全额退款。重试沿用原请求号、原金额、原支付渠道，不新建退款号。

## 2. 按业务步骤观察状态变化

以下为普通购买、主动拼团退款和主动秒杀退款的主流程。

| 步骤 | 核心调用 | 表与状态变化 | 失败后的处理 |
|---|---|---|---|
| ① 校验并保存退款意图 | `RefundTransactionService.prepare` | 锁定 `dining_order`，验证所属用户及可退款状态；创建 `refund_order.PREPARED`，业务单暂时仍为 `PAID` | 没有通过校验就不发起退款；意图持久化后会阻止核销 |
| ② 抢占并调用支付宝 | `PaymentRefundService.refundPaidPayment` | 独立提交 `refund_order: PREPARED/FAILED → PROCESSING`；先查询该退款请求，未确认成功再使用原请求号调用退款接口 | 失败原因单独提交为 `FAILED`；结果未知时也保留待办，不能据此认定支付宝一定没退款 |
| ③ 保存资金结果 | `RefundJournalService.succeeded` | 独立提交 `refund_order: PROCESSING → SUCCESS` | 此阶段提交失败时，通过原请求号重新查单确认资金结果 |
| ④ 更新本地支付单 | `RefundJournalService.completePayment` | `payment_order: SUCCESS → REFUNDED`；同一事务保存 `payment.refunded` Outbox | 本地失败后保留已经提交的退款成功记录；重试只补本地状态 |
| ⑤ 完成业务退款 | `RefundTransactionService.complete` → 原退款规则链 | 普通订单：`dining_order: PAID → REFUNDED`、退券、使用固定操作号回滚销量并归还库存；拼团：主订单、个人订单及团计数按对应策略更新；秒杀：主订单、秒杀订单及数据库活动库存一起更新 | 业务事务失败时整体回滚本地变更；已执行的商家操作通过操作号去重，后续继续补偿 |
| ⑥ 秒杀 Redis 补偿 | `OrderRefundService` → `releaseActivityStock(activityId,userId,operationId)` | 数据库提交后，Lua 使用 `REFUND:订单号` 去重，释放 Redis 库存及用户购买计数 | `refund_order` 保持未完成，后台可重放；旧退款不会释放该用户新购买的名额 |
| ⑦ 标记全链路完成 | `RefundJournalService.businessCompleted` | 核对支付单 `REFUNDED`、业务单已退款后，设置 `refund_order.business_completed=1` | 状态未一致时拒绝完成标记，继续留在补偿清单 |

业务规则链只处理本地业务补偿，使用 `requireConfirmedRefund` 检查已经保存的资金结果，不在规则链中调用支付宝。资金退款通过独立短事务留痕；Seata 不承担支付宝资金回滚，退款确认入口已经取消包围整个退款流程的全局事务。

订单取消后的晚到账通过 `ExternalPaymentService` 和 `LatePaymentReceiptService` 单独处理：先确认并记录到账，再自动退款；`dining_order` 保持 `CANCELED`，不重新恢复订单或占用库存。恢复旧实现中被回滚的晚到账支付状态时，要求已有确认成功的退款记录及对应取消订单。

拼团超时补偿继续由 `GroupBuyRepository.compensateTimeoutTeam` 处理团和个人订单，资金退款调用共用的持久化退款服务。若整团业务事务回滚，成功退款记录仍能驱动后续修复；如果团与个人订单已提交，后台核对后完成退款记录。

## 5. 后台补偿与人工处理

后台每 60 秒扫描一次未完成退款，初次请求在 2 分钟后可自动补偿；超时 2 分钟的 `PROCESSING` 可重新抢占。扫描按未完成记录及重试时间进行，不依赖最近 100 笔付款。

自动补偿最多 10 次，重试间隔逐步增长、上限 30 分钟。耗尽后保留记录和原因，由运营排查；用户再次主动申请或运营指定重试仍使用原退款号。失败记录不自动删除，也不将资金结果未知解释为未退款。

| 入口 | 用途 |
|---|---|
| `GET /api/trade/operations/refunds?limit=100` | 查询退款记录、资金结果、全链路完成标记、失败原因和补偿次数 |
| `POST /api/trade/operations/refunds/recover?limit=50` | 手动执行当前到期、尚有自动补偿次数的待办 |
| `POST /api/trade/operations/refunds/{refundOrderNo}/retry` | 排查后重试指定退款，包括已耗尽自动次数的记录 |

这些入口位于已有 `ADMIN/OPERATOR` 角色保护范围。普通用户的退款入口仍为 `/api/trade/orders/{orderId}/refund/apply`，按当前登录用户查询订单，不能通过提交他人的用户 ID 绕过归属校验。

缓存采用提交后失效、延迟再删除和 TTL，提供最终一致性；MQ 的 `SUCCESS` 表示 Broker 已接收并路由，不代表消费者业务已经完成。远程销量/库存调用使用幂等补偿，不宣称与支付宝资金或两个数据库构成原子事务。
