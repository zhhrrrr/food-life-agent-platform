# 开发日志-049-订单到店核销闭环

## 1. 本次目标

本次继续补非 Agent 业务能力，在 `food-trade-service` 内完善订单到店核销。

项目里原本已经有：

```text
OrderUseService
OrderUseCommandEntity
OrderUseResult
UseOrderResponseDTO
POST /api/trade/orders/{orderId}/use/mock
```

但之前的核销只更新 `dining_order` 主表状态，缺少核销流水，也没有同步拼团、秒杀子业务单状态。本次把它补成真正可追踪的交易闭环。

## 2. 接口

```http
POST /api/trade/orders/{orderId}/use/mock
authorization: {token}
```

说明：

```text
当前仍是 mock 核销入口。
后续接真实商家端时，需要替换为门店员工权限、核销码、设备信息和操作人审计。
```

## 3. 业务规则

```text
1. 必须登录。
2. orderId 必填。
3. 只能核销当前登录用户自己的订单。
4. 只有 PAID 订单可以核销。
5. 首次核销：dining_order.order_status PAID -> USED。
6. 首次核销：写入 order_use_record。
7. 拼团订单必须已成团，team_status = SUCCESS 才允许核销。
8. 拼团订单核销时同步 group_buy_order_list.order_status PAID -> USED。
9. 秒杀订单核销时同步 seckill_order.order_status PAID -> USED。
10. 重复核销 USED 订单返回 repeat，不重复写流水。
11. WAIT_PAY、CANCELED、REFUNDED 订单不允许核销。
```

## 4. 新增数据表

数据库：`food_trade_db`

脚本：

字段：

| 字段 | 说明 |


`uk_order_id` 用来保证同一订单只产生一条成功核销流水。

## 6. 事务边界

核销首次成功在 `OrderRepository.usePaidOrder` 一个本地事务内完成：

```text
1. CAS 更新 dining_order：PAID -> USED，并写 use_time。
2. 根据 trade_type 同步子业务单。
3. 插入 order_use_record 核销流水。
```

如果任一步失败，事务回滚。

拼团订单多一个前置条件：

```text
group_buy_order.team_status = SUCCESS
```

未成团订单即使主订单已经 PAID，也不能核销。
