# 开发日志 071：微服务边界完整性加固

## 一、本次检查结论

当前项目已经完成了比较完整的微服务改造基础：

- `food-gateway-service`：统一入口、路由、鉴权、黑名单、限流、traceId。
- `food-user-service`：用户登录、Redis Token、用户资料、关注关系。
- `food-business-service`：店铺、套餐、评价、收藏、库存能力。
- `food-trade-service`：普通订单、拼团、秒杀、支付、退款、核销、补偿。
- `food-auth-starter`：下游服务登录二次校验、Feign token 透传、内部调用密钥。
- `food-observability-starter`：Actuator、Prometheus、Micrometer Tracing、慢接口、Feign 耗时日志。
- Nacos：注册发现和配置中心。
- Sentinel：Gateway/API 限流、热点参数限流、Feign 熔断降级。
- RabbitMQ：订单超时、评价异步摘要、本地消息表和幂等消费。
- Seata：退款确认强一致链路示例。

本次重点不是继续堆技术，而是补齐两个与生产边界强相关的问题：

1. 套餐库存写接口不能继续保留在公网 Controller。
2. Gateway 请求日志不能和 observability-starter 重复治理。

## 二、为什么要收紧套餐库存接口

套餐查询属于用户侧公开能力：

```text
GET /api/package/{id}
GET /api/package/of/shop
GET /api/package/trade-snapshot/{packageId}
```

库存变更属于服务间内部能力：

```text
POST /api/internal/package/{packageId}/stock/occupy
POST /api/internal/package/{packageId}/stock/release
POST /api/internal/package/{packageId}/sold/confirm
POST /api/internal/package/{packageId}/sold/rollback
POST /api/internal/package/{packageId}/stock/adjust
GET  /api/internal/package/stock-change-records
```

原来公网 `PackageController` 里也保留了库存写接口。虽然 Gateway 黑名单可以拦截公网流量，但如果业务服务端口被误暴露，边界会变得不干净。

本次改造后：

- 公网 `PackageController` 只保留套餐查询能力。
- 库存写接口只保留在 `PackageInternalController`。
- 内部接口必须经过 `InternalCallInterceptor` 校验 `x-internal-call` 和 `x-internal-secret`。

## 三、代码变更

### 1. 收紧公网套餐 Controller

文件：

```text

```

删除公网库存写接口：

```text
POST /api/package/{packageId}/sold/confirm
POST /api/package/{packageId}/sold/rollback

```

保留公网读接口：

```text
GET /api/package/{id}
GET /api/package/of/shop
GET /api/package/trade-snapshot/{packageId}
```

### 2. 内部库存接口保留

文件：

```text
food-business-service/food-business-trigger/src/main/java/com/foodlife/business/trigger/http/PackageInternalController.java
```

当前所有库存写能力都在这里：

```text
POST /api/internal/package/{packageId}/stock/adjust
POST /api/internal/package/{packageId}/stock/occupy
POST /api/internal/package/{packageId}/stock/release
POST /api/internal/package/{packageId}/sold/confirm
```

### 3. Gateway 认证白名单精确化

文件：

```text
food-gateway-service/src/main/java/com/foodlife/gateway/properties/GatewayAuthProperties.java
food-gateway-service/src/main/resources/application-local.yml
deploy/nacos/configs/food-gateway-service.yaml
```

原来：

```text
/api/package/**
```

现在：

```text
/api/package/*
/api/package/of/shop
/api/package/trade-snapshot/*
```

这样做的含义：

- 套餐查询仍然可以免登录访问。
- 以后如果有人误加 `/api/package/**` 下的写接口，不会天然绕过 Gateway 鉴权。
- Gateway 黑名单仍然继续兜底拦截旧库存写路径。

### 4. 删除 Gateway 旧请求日志 Filter

删除文件：

```text
food-gateway-service/src/main/java/com/foodlife/gateway/filter/GatewayRequestLogFilter.java
```

原因：

- Gateway 已经引入 `food-observability-starter`。
- WebFlux 场景由 `ReactiveTraceWebFilter` 统一生成 traceId、记录请求耗时、统计慢接口。
- 旧 `GatewayRequestLogFilter` 会造成请求日志重复。

### 5. 调整 Sentinel 冒烟脚本

文件：

```text
scripts/smoke-sentinel-rules.ps1
```

套餐库存热点限流测试从公网 Gateway 路径改为内部业务服务路径：

```text
POST /api/internal/package/1/stock/occupy
```

并增加内部调用头：

```text
x-internal-call: food-life-agent
x-internal-secret: local-internal-secret
```

### 6. 新增微服务边界校验脚本

文件：

```text
scripts/verify-microservice-boundaries.ps1
```

校验内容：

```text

```

## 四、现在的真实调用边界

用户侧套餐查询：

```text
前端
 -> Gateway
 -> business-service /api/package/**
 -> PackageController
```

交易侧库存预占：

```text
前端
 -> Gateway
 -> trade-service
 -> Feign
 -> business-service /api/internal/package/{packageId}/stock/occupy
 -> InternalCallInterceptor
 -> PackageInternalController
```

退款确认释放库存：

```text
前端/运营
 -> Gateway
 -> trade-service
 -> Seata 全局事务
 -> Feign
 -> business-service /api/internal/package/{packageId}/sold/rollback
 -> business-service /api/internal/package/{packageId}/stock/release
```

## 五、面试表达

这一步可以这样讲：

项目早期为了方便验证库存能力，在公网套餐 Controller 中保留了库存写接口；微服务化以后，我把库存变更收敛到内部接口 `/api/internal/package/**`，由 Feign 自动携带内部调用密钥访问。Gateway 层保留黑名单兜底，同时把套餐白名单从 `/api/package/**` 改成精确查询路径，避免未来误把写接口暴露到公网。这样实现了“公网读接口”和“服务间写接口”的边界隔离。
