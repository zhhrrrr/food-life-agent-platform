## 三、food-auth-starter 做了什么

`food-auth-starter` 是从黑马点评登录方案中抽象出来的公共认证组件。

它的定位是：

```text
让所有 Java 业务服务都能复用同一套登录态解析逻辑，
避免每个微服务重复复制 UserHolder、RefreshTokenInterceptor、LoginInterceptor。
```

### 1. 已完成能力

当前已经完成以下类：

```text
AuthConstants
认证相关默认常量。

LoginUserDTO
登录用户轻量 DTO，只保存 id、nickName、icon。

UserHolder
基于 ThreadLocal 保存当前请求用户。

AuthProperties
认证配置类，支持配置 Token Header、Redis Key 前缀、过期时间、拦截路径。

RefreshTokenInterceptor
从请求头 authorization 获取 Token，
查询 Redis 中的登录用户信息，
写入 UserHolder，
并刷新 Token 过期时间。

LoginInterceptor
拦截必须登录的接口，
如果 UserHolder 中没有用户信息，则返回 401。

FeignAuthRequestInterceptor
微服务内部 Feign 调用时透传 authorization 请求头。

AuthAutoConfiguration
通过 Spring Boot 自动配置注册认证拦截器和 Feign 拦截器。
```

### 2. 当前认证流程

设计中的请求认证流程如下：

```text
前端请求携带 authorization Token
  -> Gateway 原样透传 authorization
  -> 业务服务引入 food-auth-starter
  -> RefreshTokenInterceptor 查询 Redis 登录态
  -> UserHolder 保存当前用户
  -> LoginInterceptor 判断是否必须登录
  -> Controller / Domain 通过 UserHolder 获取 userId
```

### 3. Redis Key 约定

当前认证组件默认使用：

```text
food:login:token:{token}
```

登录用户信息以 Redis Hash 存储：

```text
id
nickName
icon
```

### 4. 为什么这样设计

黑马点评原项目是单体应用，登录拦截器直接放在项目中即可。

当前项目是少服务微服务架构，如果每个服务都复制一套登录代码，会出现：

```text
1. 登录逻辑重复
2. Token Key 修改困难
3. UserHolder 维护分散
4. Feign Token 透传容易遗漏
5. 后期权限扩展成本高
```

所以本项目把它抽成 `food-auth-starter`，后续 `food-business-service`、`food-trade-service` 都可以直接引入。

### 5. 当前边界

当前 `food-auth-starter` 已经完成登录态解析和拦截器封装，但它不负责：

```text
1. 发送验证码
2. 校验验证码
3. 创建用户
4. 生成 Token
5. 写入 Redis 登录态
```

这些能力应该由 `food-user-service` 实现。

## 四、food-user-service 做了什么

`food-user-service` 是第一个业务微服务。

它的职责是：

```text
1. 手机号验证码登录
2. 用户资料管理
3. 用户关注关系
4. 用户基础画像
5. 对外提供用户身份相关接口
```

本次先搭建 DDD 多模块骨架，还没有完整实现登录业务。

### 1. 模块划分

当前 `food-user-service` 下包含 6 个模块：

```text
food-user-api
对外接口和 DTO。

food-user-app
Spring Boot 启动模块。

food-user-trigger
HTTP Controller、MQ Listener、Job 等入口层。

food-user-domain
用户领域模型和领域服务。

food-user-infrastructure
数据库、Redis、外部接口等基础设施适配。

food-user-types
通用响应、异常、枚举等类型。
```

### 2. food-user-api

当前定义了：

```text
IUserAuthService
LoginRequestDTO
LoginResponseDTO
```

目前接口规划：

```text
sendCode
发送手机号验证码。

login
手机号验证码登录。

logout
退出登录。
```

这一步先定义 API 形状，后续再补具体实现。

### 3. food-user-types

当前定义了统一响应对象：

```text
Response<T>
```

包含：

```text
code
message
data
```

并提供：

```text
Response.success(data)
Response.fail(code, message)
```

### 4. food-user-domain

当前先放了一个基础领域服务：

```text
AuthDomainService
```

目前只实现了手机号格式校验：

```text
isValidPhone(String phone)
```

后续这里会继续承接登录相关领域规则，例如：

```text
1. 手机号格式校验
2. 验证码有效性校验
3. 用户自动注册规则
4. 登录用户资料初始化规则
```

### 5. food-user-trigger

当前已经建立两个 Controller：

```text
HealthController
UserController
```

已提供接口：

```http
GET /health
GET /api/user/me
```

其中：

```text

用于服务健康检查。

从 UserHolder 中读取当前登录用户。
```

注意：`/api/user/me` 依赖 `food-auth-starter` 解析 Token 后写入 UserHolder。

## 七、下一步开发建议

下一步应该继续开发 `food-user-service` 的真实登录闭环。

推荐顺序：

```text
1. 从 hm-dianping 迁移 User、UserDTO、LoginFormDTO 的核心字段
2. 在 food-user-infrastructure 中建立 UserPO 和 UserMapper
3. 在 food-user-domain 中定义用户仓储接口
4. 在 infrastructure 中实现用户仓储
5. 实现 /api/user/code
6. 实现 /api/user/login
7. 登录成功后写入 Redis Hash
8. 使用 /api/user/me 验证 Token 是否能被 food-auth-starter 正确解析
```

建议优先跑通这一条链路：

```text
发送验证码
  -> 登录
  -> 返回 Token
  -> 携带 Token 调用 /api/user/me
  -> 成功拿到当前用户
```

这条链路跑通后，后续 `food-business-service`、`food-trade-service`、`python-agent-service` 才能稳定复用当前用户身份。

## 八、结论

当前两个模块的作用可以总结为：

```text
food-auth-starter
解决“其他服务如何识别当前登录用户”。

food-user-service
解决“用户如何登录并产生登录态”。
```

目前 `food-auth-starter` 已经具备基础认证能力，`food-user-service` 已经具备 DDD 骨架和启动基础。

下一步必须优先补全用户登录闭环，而不是直接开发店铺、交易或 Agent。
