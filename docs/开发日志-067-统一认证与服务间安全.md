# 开发日志-067-统一认证与服务间安全

## 本次目标

在保留黑马点评 Redis Token 登录方案的前提下，把微服务认证拆成两类：

- 用户请求：前端 -> Gateway -> 下游服务，使用 `authorization` token。
- 服务间请求：service -> service，通过 Feign 自动透传用户 token，同时增加内部调用标识和内部密钥。

这一步不把登录体系切换成 JWT。当前项目更适合继续使用 Redis Token，因为它和黑马点评登录流程、验证码登录、主动登出、滑动续期都天然匹配。

## 一、Gateway 用户请求鉴权

相关文件：

- `food-gateway-service/src/main/java/com/foodlife/gateway/filter/GatewayAuthFilter.java`
- `food-gateway-service/src/main/java/com/foodlife/gateway/properties/GatewayAuthProperties.java`

改造前，Gateway 只判断 Redis 里有没有 token key。

改造后，Gateway 会：

1. 先移除客户端传入的 `x-user-id`、`x-user-nickname`、`x-user-icon`、`x-internal-call`、`x-internal-secret`。
2. 白名单路径直接放行，但仍然使用清理后的请求头。
3. 非白名单路径读取 `authorization` 或 `Authorization: Bearer token`。
4. 从 Redis Hash `food:login:token:{token}` 读取登录用户信息。
5. Redis 用户信息不存在时返回 `401`。
6. Redis 用户信息存在时，把 token 归一化透传给下游。
7. 把可信用户上下文写入：
   - `x-user-id`
   - `x-user-nickname`
   - `x-user-icon`

这样 Gateway 成为第一层入口鉴权，下游服务仍保留第二层认证。

## 二、下游服务二次鉴权

相关文件：

- `food-auth-starter/src/main/java/com/foodlife/auth/interceptor/RefreshTokenInterceptor.java`
- `food-auth-starter/src/main/java/com/foodlife/auth/interceptor/LoginInterceptor.java`
- `food-auth-starter/src/main/java/com/foodlife/auth/context/UserHolder.java`
- `food-auth-starter/src/main/java/com/foodlife/auth/config/AuthAutoConfiguration.java`

下游服务没有完全信任 Gateway，而是继续使用 `food-auth-starter`：

1. `RefreshTokenInterceptor` 根据 `authorization` 到 Redis 查询用户 Hash。
2. 查询成功后写入 `UserHolder`。
3. 同时刷新 token TTL。
4. `LoginInterceptor` 对非白名单接口检查 `UserHolder.getUser()`。
5. 请求结束后 `afterCompletion` 清理 ThreadLocal，避免线程复用导致用户上下文泄漏。

这个设计适合面试讲“网关鉴权和服务鉴权取舍”：Gateway 做入口粗校验，下游服务做防绕过兜底。

## 三、Feign 服务间调用安全

相关文件：

- `food-auth-starter/src/main/java/com/foodlife/auth/feign/FeignAuthRequestInterceptor.java`
- `food-auth-starter/src/main/java/com/foodlife/auth/properties/AuthProperties.java`

Feign 拦截器现在做两件事：

1. 如果当前 HTTP 请求里有用户 token，自动把 `authorization` 和 `Authorization` 透传到被调用服务。
2. 每次 Feign 调用都自动增加内部调用头：
   - `x-internal-call: food-life-agent`
   - `x-internal-secret: ${FOOD_INTERNAL_SECRET:local-internal-secret}`

好处是业务代码不需要手动传 header，调用方只要声明 Feign client，服务间安全能力自动生效。

`AuthAutoConfiguration` 里注册 Feign 拦截器的条件也做了调整：只在没有同类 `FeignAuthRequestInterceptor` 时注册，不会因为未来项目里增加其他 Feign 拦截器而导致认证透传失效。

## 四、内部接口保护

相关文件：

- `food-auth-starter/src/main/java/com/foodlife/auth/interceptor/InternalCallInterceptor.java`
- `food-auth-starter/src/main/java/com/foodlife/auth/config/AuthAutoConfiguration.java`
- `food-business-service/food-business-trigger/src/main/java/com/foodlife/business/trigger/http/PackageInternalController.java`

新增 `InternalCallInterceptor`，默认拦截 `/api/internal/**`。

它不看用户 token，而是校验：

- 内部调用标识是否等于配置值。
- 内部密钥是否等于配置值。

不满足条件时返回：

```json
{"code":"403","message":"forbidden"}
```

这样内部接口不再只是“路径叫 internal”，而是真正需要服务间凭证。

## 五、库存写接口内外隔离

相关文件：

- `food-business-service/food-business-trigger/src/main/java/com/foodlife/business/trigger/http/PackageInternalController.java`
- `food-trade-service/food-trade-infrastructure/src/main/java/com/foodlife/trade/infrastructure/feign/BusinessInternalPackageClient.java`

本次把 trade-service 中这些库存写操作从公开 client 切到了 internal client：

- 库存预占：`/api/internal/package/{packageId}/stock/occupy`
- 库存释放：`/api/internal/package/{packageId}/stock/release`
- 确认售出：`/api/internal/package/{packageId}/sold/confirm`
- 售出回滚：`/api/internal/package/{packageId}/sold/rollback`
- 库存变更记录查询：`/api/internal/package/stock-change-records`

Gateway 黑名单新增：

- `/api/package/*/stock/occupy`
- `/api/package/*/stock/release`
- `/api/package/*/sold/confirm`
- `/api/package/*/sold/rollback`

因此公开网关入口不能直接调用库存变更接口；业务调用必须通过 Feign 内部路径，并带内部密钥。

## 八、面试表达

单点登录：

当前是 Redis Token 风格的分布式登录。所有服务共享 Redis 登录态，Gateway 和下游服务都按 token 查 Redis，因此多个微服务可以识别同一个用户。

JWT 和 Redis Token：

JWT 自包含、无状态、适合跨系统校验，但主动失效和服务端强控制成本更高。Redis Token 有状态，查 Redis 有网络开销，但登出、封禁、续期、黑名单更容易做。本项目沿用黑马点评方案，所以保留 Redis Token 更合适。

Token 刷新：

下游 `RefreshTokenInterceptor` 每次识别到合法 token 后刷新 Redis TTL，属于滑动过期。

网关鉴权和服务鉴权：

Gateway 负责统一入口拦截，可以减少无效流量进入业务服务；下游 auth-starter 是兜底，防止绕过 Gateway 直接访问服务。

服务间调用防伪造：

服务间 Feign 调用自动带内部标识和内部密钥。Gateway 会剥离外部请求里的内部头，避免用户伪造 `x-internal-secret`。

用户上下文传递：

Gateway 写入可信 `x-user-id` 方便日志、限流和观测；真正业务用户上下文仍由下游服务查 Redis 后写入 `UserHolder`。

ThreadLocal 泄漏：

`RefreshTokenInterceptor.afterCompletion` 调用 `UserHolder.removeUser()`，避免 Tomcat 工作线程复用时串用户。
## 九、验证补充

本次验证时发现一个容易误判的问题：登录接口本身已经在白名单内，但当请求体 JSON 解析失败后，Spring Boot 会转发到 `/error`。如果 `/error` 不在 auth-starter 白名单里，真实的 `400 Bad Request` 会被 `LoginInterceptor` 二次拦截成 `401`，排查时会误以为是登录白名单失效。

因此补充了两点：

1. `food-auth-starter` 默认白名单增加 `/error`。
2. 三个业务服务和 Gateway 的本地/Nacos 配置显式增加 `/error`。

同时修正了 `scripts/smoke-auth-internal-security.ps1` 在 Windows PowerShell 下调用 `curl.exe` 的 JSON 转义问题。脚本现在先把 JSON 请求体写入临时文件，再通过 `--data-binary @file` 提交，避免双引号被命令行吞掉。

最终验证结果：

```text
mvn test                                    SUCCESS
mvn clean install -DskipTests               SUCCESS
scripts/smoke-gateway.ps1                   SUCCESS
scripts/smoke-auth-internal-security.ps1    SUCCESS
scripts/smoke-seata-demo.ps1                SUCCESS
```
