# P0 生产化联调与接口契约

本次 P0 不接真实支付宝或微信支付，目标是把现有本地支付从简单 mock 推进到可联调、可校验、可复盘的业务骨架。

## 1. 本地支付边界

支付渠道仍然是 `LOCAL_PAY`，但支付成功回调不再只相信前端传参。回调必须携带：

```json
{
  "payOrderNo": "PAY...",
  "outTradeNo": "OUT...",
  "payAmount": 16800,
  "signType": "SHA256",
  "signature": "sha256 hex"
}
```

签名明文：

```text
payOrderNo|outTradeNo|payAmount|LOCAL_PAY|local-payment-secret
```

配置位置：

```text
food-trade-service/food-trade-app/src/main/resources/application-local.yml
deploy/nacos/configs/food-common.yaml
```

对应代码：

```text
LocalPaymentProvider.verifyPaySuccessCallback
LocalPaymentProvider.refund
PaymentController.toCallbackCommand
```

## 2. 退款单骨架

用户退款现在会创建 `refund_order`，然后走支付 Provider 的退款能力，再把支付单标记为 `REFUNDED`。

核心状态：

```text
PREPARED -> SUCCESS
PREPARED -> FAILED
```

关键幂等：

```text
refund_order.uk_refund_order_no
refund_order.uk_pay_order_no
```

也就是说，同一笔支付单只能生成一笔退款单。重复退款时，业务会优先读取已有退款记录。

## 3. 权限模型表驱动

登录仍沿用黑马点评的 Redis Token 方案，但用户角色不再写死为 `USER`。

新增表：

```text
food_user_db.user_role
```

登录时：

```text
UserAuthController -> IUserRoleRepository.findHighestRoleCodeByUserId -> Redis token hash role
```

网关和下游服务继续读取 token 中的 `role` 完成运营接口鉴权。

## 4. 接口契约与错误码

统一 Response 结构保持不变：

```json
{
  "code": "0000",
  "message": "success",
  "data": {}
}
```

本次补充的业务错误码：

```text
ORDER_409    订单状态不允许当前操作
PAYMENT_401  支付回调签名错误
PAYMENT_502  支付退款失败
```

接口契约入口：

```text
http://localhost:8301/swagger-ui.html
http://localhost:8301/v3/api-docs
```

网关路由后仍可通过统一入口访问业务接口：

```text
http://localhost:8080/trade-api/**
```
