# 开发日志-089-运营审计查询前端闭环

## 背景

trade-service 已经在支付准备、支付回调、取消订单、申请退款、退款确认、核销、运营库存调整等写操作中记录 `trade_operation_audit_log`。

之前的问题是：审计数据虽然已经入库，但运营侧没有页面入口，只能直接查数据库。这不符合公司项目里“可排查、可追踪、可运营”的要求，也不利于后续 Agent 写操作审计。

本次改造补齐前端运营审计闭环。

## 本次改造

文件：

- `food-life-agent-web/src/types/order.ts`

新增：

- `OperationAuditLog`

字段覆盖：

- `operatorRole`
- `operationType`
- `bizType`
- `bizId`

- `requestContent`

### 2. 前端新增审计 API

文件：

- `food-life-agent-web/src/api/trade.ts`

新增：

```ts
queryOperationAuditLogs(params)
```

调用 Gateway 路径：

```text
GET /trade-api/operations/audit-logs
```

Gateway 再转发到 trade-service：

```text
GET /api/trade/operations/audit-logs
```

### 3. 新增运营审计页面

文件：

- `food-life-agent-web/src/views/OperationAuditView.vue`

能力：

- 按 `traceId` 查询。
- 按 `operatorId` 查询。
- 按 `operationType` 查询。
- 按 `bizType` 查询。
- 按 `bizId` 查询。
- 控制查询 `limit`，范围 10 到 200。
- 卡片式展示审计记录。
- 展示请求快照和响应快照。
- 支持点击复制 `traceId`。

### 4. 新增路由和前端角色保护

文件：

- `food-life-agent-web/src/router/index.ts`

新增路由：

```text
/operations/audit
```

并增加：

```ts
meta.requiresOperator = true
```

路由守卫会在进入运营页前拉取当前用户信息，并检查：

```text
ADMIN
OPERATOR
```

普通用户不展示入口，也不能从前端直接进入页面。

注意：前端角色保护只负责体验，真正权限仍由后端 `food-auth-starter` 的角色拦截器兜底。

### 5. 顶部导航新增审计入口

文件：

- `food-life-agent-web/src/layouts/AppLayout.vue`

新增计算属性：

```ts
canViewOperations
```

只有当前用户角色是 `ADMIN` 或 `OPERATOR` 时，顶部导航才显示“审计”入口。

### 6. user-service 返回角色信息

文件：

- `food-life-agent-web/src/types/user.ts`
- `food-user-service/food-user-app/src/main/resources/application-local.yml`
- `deploy/nacos/configs/food-user-service.yaml`

前端 `CurrentUser` 增加 `role` 字段。

user-service 的 local 和 Nacos 配置增加：

```yaml
food:
  auth:
    role-access:
      default-role: USER
      local-user-roles:
        1: ADMIN
```

原因是 trade-service 已经知道本地用户 `1` 是 ADMIN，但前端角色来源是 `/api/user/me`。如果 user-service 不配置同样的本地角色映射，前端拿到的角色可能仍是 `USER`，导致运营入口不显示。

### 7. 新增专项验证脚本

文件：

- `scripts/verify-operation-audit-ui.ps1`

并接入：

- `scripts/verify-company-readiness.ps1`

验证内容：

- 前端 trade API 必须存在审计查询方法。
- 审计 API 必须通过 Gateway `/trade-api/operations/audit-logs`。
- 前端必须定义审计类型。
- 路由必须存在 `/operations/audit`。
- 路由必须带 `requiresOperator`。
- 路由守卫必须先拉取当前用户再判断角色。
- 顶部导航必须按角色显示运营入口。
- user-service local 和 Nacos 配置必须把本地用户 `1` 映射为 `ADMIN`。

### 8. 修复公司级验证脚本的失败透传

文件：

- `scripts/verify-company-readiness.ps1`

新增 `Invoke-CheckedNative`，用于执行 Maven 和 npm 命令。

原因：

- PowerShell 的 `$ErrorActionPreference = "Stop"` 不能自动保证所有 native command 失败都会让脚本失败。
- 本次验证时发现 Maven 测试失败后，脚本仍继续执行前端构建并最终打印完成信息。
- 修复后，`mvn test` 或 `npm run build` 任一失败，脚本都会直接抛错。

### 9. 修复支付 Provider 单测兼容问题

文件：

- `food-trade-service/food-trade-infrastructure/src/test/java/com/foodlife/trade/infrastructure/payment/LocalPaymentProviderTest.java`

调整：

```java
List.of(localPaymentProvider)
```

改为：

```java
Collections.singletonList(localPaymentProvider)
```

原因：

- 当前 Maven 测试链路里该用法触发编译识别问题。
- 使用 `Collections.singletonList` 更稳，不影响测试语义。

## 当前请求链路

```text
前端 OperationAuditView
  -> queryOperationAuditLogs
  -> Gateway /trade-api/operations/audit-logs
  -> trade-service /api/trade/operations/audit-logs
  -> OperationAuditController
  -> OperationAuditDomainService
  -> IOperationAuditRepository
  -> OperationAuditRepository
  -> trade_operation_audit_log
```

## 和 Agent 的关系

后续 Agent 执行写操作时，尤其是退款、库存调整、核销这类敏感动作，也需要进入同一套审计模型。

这一步先把“人操作”的审计查询打通，后续只需要增加：

- `operatorRole = AGENT`
- `operatorId = agentUserId`
- `operationType = AGENT_TOOL_xxx`
- `requestContent` 记录工具入参
- `responseContent` 记录工具执行结果

就能复用当前审计查询页面和审计表。
